# SubReel Launcher — дорожная карта

Документ описывает, что уже сделано при модернизации v14 → v15, что осталось доделать в рефакторинге и в каком порядке строить игровое ядро (уровень Prism Launcher / MultiMC). Порядок выбран по зависимостям между модулями: сначала то, без чего не работает остальное.

Состояние сборки на момент написания: код этапов 1–4 написан, но не проверен компилятором в среде автора (нет .NET SDK). Любой этап считается закрытым только после `dotnet build` и `dotnet test` у владельца проекта.

## 3. Игровое ядро: модули и порядок

Правило границ проектов: **новый проект создаётся, когда в нём появляется первый реальный код с потребителем**, а не заранее. До этого контракты лежат папками в `SubReel.Launcher.Application`.

### 3.1 Граф зависимостей

```
Instance Management ──┬──► Java Manager ──┐
                      │                   │
Download Manager ─────┼──► Library Mgmt ──┼──► Minecraft Installation ──► Game Launcher
                      └──► Asset Mgmt ────┘                                   ▲
Authentication ───────────────────────────────────────────────────────────────┘
Mod Loader Integration ──► Mod Manager ──► Plugin System
```

### 3.2 Фазы

**Фаза 5. Download Manager и Instance Management** (основа всего)
- *Download Manager*: очередь загрузок с общим лимитом параллелизма, проверка SHA-1 и размера, докачка, повтор с паузой, прогресс и отмена через `CancellationToken`. `DiskImageCache` уже содержит нужные приёмы (дедупликация одинаковых URL, общий лимит, атомарная запись через `.tmp`); общий механизм выделяется из него, а не пишется параллельно.
- *Instance Management*: экземпляр = папка с версией, загрузчиком, своими настройками (память, аргументы JVM, Java), модами и сохранениями. Хранится в JSON через `JsonFileStore` (атомарная запись, `SchemaVersion`). Модель `Instance` — в Domain, `IInstanceRepository` — в Application.
- Первый проект: `SubReel.Launcher.Minecraft` (Download + Instances), так как появляется реальный код.
- Интерфейс: экран экземпляров; кнопка «Создать сборку» перестаёт быть демо.

**Фаза 6. Version Management (установка) + Library и Asset Management**
- Читать `version.json` версии (из каталога Mojang): клиентский jar, список библиотек с правилами (`rules` по ОС и архитектуре), нативные библиотеки, индекс ассетов, конфигурация логирования, `mainClass`, аргументы.
- Скачивать клиент, библиотеки, ассеты через Download Manager; распаковывать нативные библиотеки в папку экземпляра.
- Общий кэш библиотек и ассетов между экземплярами (как у Prism): один файл на диске, ссылки из экземпляров.
- Проверка целостности перед запуском («Проверка файлов...» в `LaunchViewModel` становится настоящей).
- Наследование версий (`inheritsFrom`) нужно сразу: от него зависят Fabric/Forge.

**Фаза 7. Java Manager**
- Обнаружение установленных Java (реестр Windows, `JAVA_HOME`, типовые папки) и чтение версии.
- Загрузка Java-рантайма, который указывает версия Minecraft (`javaVersion` в `version.json`); хранение в `%LocalAppData%\SubReel\runtimes`.
- Правило подбора: версия Minecraft → требуемая мажорная версия Java → найденная или загруженная.
- Экран «Настройки»: выбор Java, память — значения сохраняются в настройках и настройках экземпляра.

**Фаза 8. Authentication** (выполнена в этапе 8: см. ARCHITECTURE.md)
- Контракты в Application: `IAccountProvider`, `ISession`; офлайн-аккаунты уже есть (`AccountService`).
- Microsoft-аккаунт: вход через Microsoft → Xbox Live → XSTS → Minecraft Services, затем профиль и проверка владения игрой. Реализация — отдельный проект `SubReel.Launcher.Authentication`.
- **Хранение токенов отдельно от `design-settings.json`**: защищённое хранилище Windows (DPAPI или Credential Manager), в журнал токены не попадают. Формат настроек не меняется: в нём остаются только ник и оформление.
- Обновление токена в фоне, обработка истёкшей сессии без потери аккаунта.
- Перед реализацией проверить текущие требования Microsoft к регистрации приложения (идентификатор клиента, разрешённые сценарии входа): они менялись.
- SubReel ID — после появления бэкенда `subreel-platform`.

**Фаза 9. Game Launcher**
- Сборка командной строки: JVM-аргументы, classpath, `mainClass`, аргументы игры с подстановкой (`${auth_player_name}`, `${assets_root}` и т. д.), оффлайн/онлайн-сессия.
- Запуск процесса, перехват вывода игры в журнал экземпляра, статусы «запускается / запущена / закрыта / упала», код завершения.
- `LaunchViewModel` подключается к настоящему запуску; демо-прогресс удаляется.
- Проект `SubReel.Launcher.Minecraft` получает модуль запуска; зависимость от Authentication — только через контракт сессии.

**Фаза 10. Mod Loader Integration**
- Fabric и Quilt: профиль версии берётся с их мета-серверов, дальше устанавливается как обычная версия с `inheritsFrom`.
- Forge и NeoForge: установщик с обработчиками (processors) — самая сложная часть; отдельная фаза внутри этапа.
- Выпадающий список версий в подвале (Vanilla / Fabric / Forge / NeoForge) начинает показывать не только найденные в папке `.minecraft`, но и устанавливаемые.

**Фаза 11. Mod Manager**
- Источники модов: Modrinth (открытый API), CurseForge (нужен ключ API и условия использования — проверить до начала).
- Установка, обновление, удаление, проверка совместимости с версией и загрузчиком, зависимости между модами.
- Проект `SubReel.Launcher.Mods`; интерфейс — экран модов экземпляра и «Mod Studio» в Hub.

**Фаза 12. Plugin System**
- Стартует только после того, как у ядра есть стабильные контракты. Ранний плагинный API придётся ломать.
- Минимум: загрузка сборок из папки `plugins`, изолированный `AssemblyLoadContext`, манифест (имя, версия, требуемая версия API), точки расширения (источники новостей, источники модов, страницы Hub).
- Безопасность: плагины запускаются с правами пользователя, поэтому нужны явное разрешение пользователя и подпись или список доверенных; решение принять до начала работ.

**Фаза 13. SubReel Studio Hub**
- *Server Studio*: локальный сервер (версия, загрузчик, параметры, старт/стоп) — использует Version Management, Java Manager и Download Manager; позже перенос на хостинг.
- *Skin Studio*, *Mod Studio*: после Authentication и Mod Manager соответственно.
- До готовности инструменты остаются на странице «В разработке» и не имитируют работу.

## 4. Сквозные правила для каждой фазы

1. Контракт (интерфейс + модели) пишется вместе с первым потребителем и тестом, без интерфейсов «на будущее».
2. Данные пользователя: новый формат — только с `SchemaVersion`, атомарной записью и миграцией; старые файлы не теряются.
3. Асинхронность: каждая длительная операция принимает `CancellationToken`, не блокирует UI, не использует `async void` и `_ = Task`.
4. Ошибки: ожидаемые сбои обрабатываются по типам исключений и пишутся в журнал; пустых `catch` нет.
5. Тесты: unit-тесты на правила и разбор данных; интеграционные — на временной папке и заглушке HTTP (`StubHandler`), без реальной сети.
6. Дизайн: новые экраны используют существующие `Theme.xaml`, `ControlStyles.xaml` и шаблоны; готовые анимации и навигация не переписываются.
7. Внешние API (Mojang, Microsoft, Fabric, Forge, Modrinth, CurseForge) проверяются по актуальной документации в начале соответствующей фазы: форматы и условия меняются.
8. Каждая фаза закрывается сборкой и тестами у владельца, затем архивом `SubReel_Launcher_v15_*`.

## 5. Риски

| Риск | Мера |
|---|---|
| Код пишется без компилятора, ошибки накапливаются | короткие этапы, сборка после каждого, архив только по готовому этапу |
| Forge/NeoForge установщики сложны и часто меняются | отдельная фаза, начинать с Fabric/Quilt |
| Утечка токенов Microsoft-аккаунтов | защищённое хранилище, токены не в настройках и не в журнале |
| Лицензионные условия CurseForge и ключ API | выяснить до начала Mod Manager, начать с Modrinth |
| Плагины расширяют поверхность атаки | поздняя фаза, явное согласие пользователя |
| Рост числа ViewModel | пересмотр CommunityToolkit.Mvvm в этапе 4 |
